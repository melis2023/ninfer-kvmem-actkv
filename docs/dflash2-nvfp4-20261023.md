# DFlash2 NVFP4 草稿支持（2026-10-23）

引擎现在可以直接加载 **NVFP4 编码的 DFlash2 草稿**，并把 `attention/output` 与
`mlp/down` 以 NVFP4 权重跑在动态卷积的 finish 路径上。

## 推荐草稿地址

DFlash2 草稿优先使用这个 ModelOpt NVFP4 版本：

- <https://huggingface.co/maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal/tree/main>

它是已经编码好的 NVFP4（`weight` 为 U8 packed codes、`weight_scale` 为 E4M3、
`weight_scale_2` 为 FP32 全局除数），转换时**原样导入，不做二次量化**。

其他来源的 DFlash2 草稿（BF16 / per-row FP8 / GGUF）可以作为备选，但只有这个
ModelOpt NVFP4 目录能走无损导入路径。

## 引擎改动

| commit | 内容 |
|---|---|
| `f4d18713` | 在 NVFP4 线性分发表里注册 DFlash2 的五个几何：Feature `25600x5120`、QKV `6144x5120`、AttnOut `5120x4096`、ConvProj `1280x5120`、Selector `256x5120`，own 与 unified 两条调度路径都注册 |
| `18e3c7c8` | 动态卷积的 add 路径接受 NVFP4 父权重（按 `n/k` 校验后走 materialized linear + conv finish）；补上转换用的两个 recipe |

### 为什么必须改 conv

`linear dynamic grouped conv add` 原先只接受 `Q8_G32_FP16`，而 ModelOpt NVFP4 草稿把
`attention/output`（`5120x4096`）和 `mlp/down`（`5120x17408`）都导出为 NVFP4，启动时
warmup 直接失败：

```
ERROR engine | worker crash: linear dynamic grouped conv add: invalid projection_weight
```

现在 NVFP4 走 `materialized_projection` 分支：先做一次普通 linear 得到 BF16 投影，
再跑 conv finish，与 Q8 路径的结果语义一致。

注意 `kernel_projection`（`1280x5120`）仍然必须是 **BF16**，因为它的 prepare 路径
（`dynamic grouped conv prepare`）没有 NVFP4 内核。转换配方已经跳过它。

## 转换用法

前提：`backends/ninfer` 的 `tools/convert` 环境就绪（Python 3.11 + PyTorch），
并且在 `infer-convert`（或 `backends/ninfer`）目录下执行。

```bash
python3 -m tools.convert \
  --model /path/to/conversion-input/metadata \
  --recipe qwen3_8_27b_gguf \
  --source gguf=Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf \
  --source dflash2=/path/to/Qwen3.8-27B-DFlash2-NVFP4-RTNcal \
  --override tools/convert/recipes/dflash2_import_nvfp4.py \
  --components text,mtp,dflash2 \
  --device cpu \
  --name qwen3.8-27b-dflash2-nvfp4 \
  --out model.ninfer
```

关键点：

- `--override .../dflash2_import_nvfp4.py` 是**无损导入**，保留源里的 codes、E4M3
  块缩放和 FP32 除数；不加它则会按普通权重重新量化。
- `dflash2_nvfp4.py` 是另一条路：把 BF16 / per-row FP8 草稿重新量化为 NVFP4。
  两条 recipe 都已跳过 `kernel_projection`，保持 BF16。
- QKV 不参与 NVFP4：引擎的融合 attention 输入投影要求 `Q8_G32_FP16`，且本模型的
  QKV 几何是 `6144x5120`（引擎的 NVFP4 QKV 快路径只覆盖 `4096x5120`）。
- `feature_projection` 保持 W8，`candidate_selector/hidden_projection` 保持 BF16。

## `.safetensors` 格式限制

DFlash2 源必须是转换器认识的 safetensors 布局，目前只有三种：

| 格式 | 特征 | 处理方式 |
|---|---|---|
| **ModelOpt NVFP4** | `quantization_config.quant_algo = NVFP4`；张量为 `weight`(U8) + `weight_scale`(E4M3, K16) + `weight_scale_2`(F32 divisor) | 原样导入（推荐） |
| **BF16** | 普通 BF16 权重，无量化配置 | 反量化后重新量化为 NVFP4 |
| **per-row FP8** | `quant_method = fp8`，每行一个 `weight_scale` | 反量化后重新量化为 NVFP4 |

**不支持**的常见变体：

- **128×128 block FP8（DeepSeek 风格）**：`weight_block_size: [128, 128]`，
  scale 名为 `weight_scale_inv`（F32，且是倒数）。转换器只认 per-row 的
  `weight_scale`，会报：

  ```
  ValueError: ... missing source tensor 'layers.0.mlp.gate_proj.weight_scale'
  ```

  这类源需要先自行反量化成 BF16 safetensors，再走第二个配方。
- **GGUF 形式的 NVFP4**：ggml type 40 是 64 元素 / 36 字节的 super-block
  （4 个 E4M3 scale + 32 字节 code），与 ninfer 的 `BlockScaleK16M128x4`
  布局不同，不能直接映射。本仓库不提供 GGUF NVFP4 的直通导入。

## 实测（64K，RTX 5060 Ti 16 GB）

条件：`--max-context 65536 --kv-dtype nvfp4`，KVMem 默认（未启用），
prompt 62,259 token，输出 256，temperature 0。

| 后端 | draft | CUDA graphs | decode | 接受率 |
|---|---|---|---:|---:|
| dflash2 | 4 | 关（64K 必须关） | **52.7 tok/s** | 44.0% |
| dflash2 | 3 | 关 | 51.3 tok/s | 52.9% |
| mtp | 3 | 开 | 49.7 tok/s | 54.7% |
| mtp | 3 | 关 | 49.1 tok/s | 54.7% |

推荐参数：

```
--kv-dtype nvfp4 --no-cuda-graph \
--spec dflash2 --draft-tokens 4 --full-draft-head
```

### 显存约束

DFlash2 权重比 MTP 多约 1.1 GiB。64K 上下文 + nvfp4 KV 时：

- 开 CUDA graphs：需要 2.92 GB，仅 2.46 GB 可用 → 启动失败
- 关 CUDA graphs：1.78 GiB runtime，free 约 634 MiB → 可用

所以 64K 下必须 `--no-cuda-graph`；如果降到约 33K 上下文，可以开图再多约 6% 速度。

### 参数规律

- draft 深度：`4 > 3 > 5 > 6 > 7`（4 为峰值）
- `--full-draft-head` 比默认 proposal head 快约 2.3%
- `--ngram-draft-tokens` 默认 15 最优；关掉或加到 31 都更慢（纯文本场景）
- 接受率上限约 44%，参数层面已经榨干，继续提速只能换更好的草稿权重
